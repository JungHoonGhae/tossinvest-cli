# API 변경 분석 — 2026-08-12

> breaking-risk

## 0. 스코프

공식 Open API spec 스냅샷 갱신(`6386f11`, 자동화 워크플로 커밋)만 대상.
`info.version` **1.2.13 → 1.2.14** (패치 범프). `docs/migration/.openapi-snapshot.json` 의
`spec_path_count` 는 **33 → 33 로 불변** — 경로 추가/삭제는 없다. 순수 스키마
description/example 수정 + 버전 번호 변경뿐이다.

## 1. 변경 요약

diff 는 `components.schemas.Commission.properties.commissionRate` 한 곳(과 그 필드를
쓰는 응답 예시 2곳)뿐이다.

| 항목 | 이전 (1.2.13) | 이후 (1.2.14) |
|---|---|---|
| `description` | "수수료율 (%). 예: 0.015는 0.015%" | "매매 수수료율 (소수 비율). 예: `0.00015` = 0.015%" |
| `example` | `"0.015"` | `"0.00015"` |
| `GET /api/v1/commissions` 응답 예시(KR) | `commissionRate: "0.015"` | `commissionRate: "0.00015"` |
| `GET /api/v1/commissions` 응답 예시(US, 두 케이스) | `"0.1"` / `"0.25"` | `"0.001"` / `"0.0025"` |

필드 `type`(`string`, `format: decimal`)과 `required` 여부는 그대로다. 즉 **스키마
구조상 breaking 은 아니다** — 바뀐 건 "같은 문자열 필드에 담기는 값의 의미(스케일)"뿐.

이전 설명은 "0.015 라는 값 자체가 0.015%를 뜻한다"(퍼센트 숫자를 그대로 문자열화)였고,
새 설명은 "0.00015 라는 값이 0.015%를 뜻한다"(소수 비율, ×100 해야 퍼센트)로 바뀌었다.
같은 실물 수수료(0.015%)를 나타내는 문자열이 100배 차이 나게 된 것 — 두 표기가 동시에
맞을 수는 없으므로, 이전 문서가 틀렸던 걸 이번에 고쳤거나(문서 정합성 수정) 실제 서버
응답값의 스케일이 바뀐 것(행동 변경) 둘 중 하나다. 레포 파일 분석만으로는 어느 쪽인지
확정할 수 없다.

## 2. tossctl 커버리지 대조

`GET /api/v1/commissions` 는 `internal/official/commissions_reads.go` 의
`Commissions()` 가 이미 구현·소비 중이다.

| 위치 | 현재 상태 | 새 스펙과의 관계 |
|---|---|---|
| `internal/official/commissions_reads.go:16` (주석) | `commissionRate string (decimal) — e.g. "0.015" (1.5%)` | **새 스펙과 불일치.** 이 주석은 "0.015 = 1.5%"(값을 100으로 나눠야 퍼센트)를 전제하는데, 이는 이전 스펙("0.015 = 0.015%", 나눌 필요 없음)과도, 새 스펙("0.00015 = 0.015%")과도 다르다. 애초에 주석 자체가 스펙 어느 버전과도 안 맞았던 걸로 보인다 |
| `internal/official/commissions_reads.go:52` `adaptCommissions` | `parseDecimal(raw[0].CommissionRate)` — 문자열을 그대로 float 로 파싱, 스케일 보정 없음 | 서버가 주는 값을 가공 없이 그대로 `domain.Commission.CommissionRate` 에 싣는다. 스케일 해석은 전적으로 출력 단계(`formatPercent`)에 위임됨 |
| `internal/output/marketdata.go:627-630` `formatPercent` | `rate*100` 후 `%` 접미 — **"값은 소수 비율"이라는 전제로 동작** | 새 스펙("소수 비율")과는 정합. 구 스펙("퍼센트 숫자 그대로")이 실제 서버 동작이었다면, 이 출력 함수는 지금까지 KR 케이스에서 100배 부풀린 값(0.015% 를 1.5%로)을 보여줬을 가능성이 있음 |
| `internal/official/commissions_reads_test.go` | 입력·출력 모두 `"0.015"` → `0.015` 로만 검증 | 순수 pass-through 검증이라 어느 스케일 해석이 맞는지는 테스트로 보장되지 않음 — 이번 이슈를 못 잡는 구조 |
| `internal/client/marketdata.go:672`, `internal/ops/wts_operations.go:658` (`commissionInfoKr.commissionRate`) | 별개의 WTS 내부 API(`number` 타입) 를 쓰는 다른 코드 경로 | 이번 공식 Open API 스펙 변경과 무관 — 영향 없음 |

정리하면: **필드 타입/필수 여부 변경은 없어 구조적으로는 no-op** 이지만, 값의 의미
(스케일)에 대한 스펙 서술이 바뀌었고 그게 우리 코드 주석·출력 로직의 전제와 사실상
어긋난다. 실계좌/라이브 호출이 금지된 이번 스텝에서는 실제 프로덕션 응답이 어느
스케일을 쓰는지 확인할 수 없다.

## 3. 분류

**(c) breaking 위험** (좁은 의미의 스키마 breaking 은 아니지만, 사용자에게 보여주는

분류한다). 엔드포인트/필드 추가·삭제는 없음.

## 4. 권장 후속 조치

1. **실제 응답 스케일 확인**: 안전한(비계좌) 방식으로 `/api/v1/commissions` 를 한 번
   호출해 실제 `commissionRate` 문자열 형식이 `"0.00015"` 류(소수 비율)인지
   `"0.015"` 류(퍼센트 숫자)인지 확인 필요. 이번 스텝은 레포 파일 분석만 수행했으므로
   라이브 검증은 후속 스텝(또는 사람)이 수행.
2. `internal/official/commissions_reads.go:16` 의 주석을 새 스펙 문구("소수 비율,
   예: 0.00015 = 0.015%")에 맞춰 갱신 — 현재 주석은 구/신 스펙 어느 쪽과도 안 맞아
   그 자체로 오해 소지가 있다.
3. `commissions_reads_test.go` 에 "실물 0.015% 가 정확히 0.015% 로 표시되는지"를
   검증하는 회귀 테스트를 추가할 것 — 지금은 pass-through 만 검증해 스케일 버그를
   못 잡는다. 1번에서 확인한 실제 값으로 fixture 를 갱신.
4. 1번 확인 결과 실제로 서버 값 스케일이 바뀐 것으로 판명되면(구 스펙 기준 프로덕션이
   `"0.015"` 를 반환해 왔다면), `formatPercent` 소비 지점에서 과거 사용자에게 100배
   부풀린 수수료율이 노출돼 왔을 가능성 — 별도 버그 리포트/핫픽스 검토 필요.
