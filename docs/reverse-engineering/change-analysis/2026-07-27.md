# API 변경 분석 — 2026-07-27

## 1. 변경 요약

커밋 `5607f4f` (`docs(migration): openapi-snapshot 자동 갱신`)에서 `docs/migration/openapi.latest.json` 이 갱신되었다. 변경 내용은 두 곳뿐인 작은 diff.

- `info.version`: `1.2.4` → `1.2.5`
- `components.schemas.PaginatedOrderResponse.description` 변경:
  - 이전: `status=CLOSED` 호출 시 `400 closed-not-supported` 를 반환한다고 명시.
  - 이후: `status=CLOSED` 도 `limit` 단위로 페이징하며, 다음 페이지가 있으면 `nextCursor`/`hasNext=true` 가 내려온다고 명시.

즉 `GET /api/v1/orders` (일반 주문 목록) 엔드포인트에서 `status=CLOSED` 필터가 더 이상 에러를 반환하지 않고, 조건주문 목록(`/api/v1/orders/conditional`)과 동일한 커서 기반 페이지네이션을 지원하게 되었다. 요청/응답 스키마(필드, 타입)나 경로 자체의 변경은 없고 설명(description) 텍스트만 바뀐 **동작 변경 공지**다. 신규/삭제 엔드포인트는 없다.

## 2. tossctl 커버리지 대조

`internal/official/orders_reads.go` 의 `Client.Orders()` 를 확인:

- `OrdersFilter` 는 이미 `Cursor`, `Limit` 필드를 갖고 있고, 내부 `apiOrderPage` 구조체도 `NextCursor`/`HasNext` 를 JSON 언마샬링한다 (`orders_reads.go:59-63`, `76-79`).
- 그러나 `Orders()` 의 반환 타입은 `[]domain.Order` 뿐이며, 마지막에 `adaptOrders(raw.Orders)` 만 반환하고 `raw.NextCursor`/`raw.HasNext` 는 그대로 버려진다 (`orders_reads.go:106-111`). 즉 **페이지네이션 메타데이터가 호출자에게 전혀 노출되지 않는다.**
- `internal/ops/read_operations.go:118-152` 의 MCP/ops 카탈로그 `orders` 오퍼레이션은 `cursor`/`limit` 파라미터를 받아 `official.OrdersFilter` 에 그대로 꽂아 `d.Client.Orders(ctx, f)` 를 호출하지만, 반환값 역시 `[]domain.Order` 이므로 `hasNext`/`nextCursor` 를 클라이언트(에이전트/CLI 사용자)가 알 수 있는 방법이 없다.
- 대조군으로 조건주문 쪽(`internal/official/conditional_reads.go:42-73`, `domain.ConditionalOrderList` — `internal/domain/models.go:799-800`)은 이미 `NextCursor`/`HasNext` 를 포함한 리스트 타입을 반환하도록 올바르게 구현되어 있다. `cmd/tossctl/order.go` 의 `order conditional list` 서브커맨드도 `--cursor`/`--limit` 플래그를 노출한다.
- 반면 일반 주문(`/api/v1/orders`)을 다루는 CLI 서브커맨드(`cmd/tossctl/order.go`, `cmd/tossctl/orders.go`)는 전부 WTS 어댑터(`ListPendingOrders`/`ListCompletedOrders`, `internal/client/`)를 사용하며 공식 API(`official.Client.Orders`)는 현재 `internal/ops` 카탈로그(MCP 서버 / `tossctl ops call orders`) 경로로만 호출된다.

## 3. 분류

**(b) 신규 기능 후보** — 크래시나 기존 정상 동작의 손상은 없다(`status=OPEN` 경로는 그대로 동작). 다만 기존에 `status=CLOSED` 는 항상 `400 closed-not-supported` 로 실패했으므로 실사용 경로가 없었고, 이번 변경으로 처음 "성공 응답"이 되는 케이스다. 그런데 우리 `Client.Orders()` 구현은 이미 `Cursor`/`Limit` 요청 파라미터와 응답의 `NextCursor`/`HasNext` 파싱 코드를 갖추고 있음에도 반환 시 페이지 메타데이터를 버리고 있어, `status=CLOSED` 로 다건(페이지 크기 초과) 조회 시 **첫 페이지만 조용히 반환되고 이후 페이지가 있는지조차 알 수 없는** 상태다. 크래시는 아니지만 데이터 완결성 관점에서 사용자를 오도할 수 있는 잠재적 결함이므로 breaking-risk 로 표시하지는 않되, 후속 조치가 필요하다고 판단한다.

## 4. 권장 후속 조치

1. `official.Client.Orders()` 의 반환 타입을 `domain.ConditionalOrderList` 와 같은 패턴(예: `domain.OrderList{ Orders []domain.Order; NextCursor string; HasNext bool }`)으로 바꾸어 `status=CLOSED` 페이지네이션 메타데이터를 호출자에게 노출한다.
2. `internal/ops/read_operations.go` 의 `orders` 오퍼레이션 핸들러와 그 문서/스키마(Summary, Params)를 갱신해 `hasNext`/`nextCursor` 가 응답에 포함됨을 명시한다.
3. 필요 시 `tossctl order` 계열에 공식 API 기반의 `CLOSED` 주문 목록 조회 서브커맨드(조건주문의 `order conditional list --status CLOSED --cursor ...` 와 동일한 UX)를 추가하는 것을 검토한다.
4. `internal/official/orders_reads_test.go` 에 `status=CLOSED` + `hasNext=true` 응답을 모킹한 회귀 테스트를 추가해 페이지네이션 필드 누락을 방지한다.
5. 위 항목들은 기존 동작을 깨지 않는 순수 확장이므로 다음 정기 개발 사이클에 반영해도 무방하다. 실계좌 데이터/라이브 API 호출 없이 목(mock) 기반 테스트로 검증할 것.
