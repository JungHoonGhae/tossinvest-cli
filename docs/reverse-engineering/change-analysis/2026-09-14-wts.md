# WTS 주문 API 변경 분석 — 2026-09-14

## 결론

신규 미체결 v2·완료 v3 경로 발견은 기존 CLI 경로의 폐기를 뜻하지 않는다.
활성 빌드 `zohm1Acaa2LR63_36yS6O`에는 기존 미체결 v1과 기간별 완료 주문 v2의
호출 코드가 함께 남아 있다. 신규 API는 별도 계약으로 조사하며 현재 경로를 유지한다.

확인된 런타임 문제는 주문 목록이 누락된 HTTP 200 응답을 정상적인 빈 내역으로
처리한다는 점이다. v0.51.1에서 누락·`null` 목록을 오류로 거절하도록 수정했다.
이는 합성 HTTP 응답으로 재현한 문제이며, 실제 서버에서 같은 응답을 관측했다는 뜻은 아니다.

v3 완료 주문 호출부는 조건에 따라 `market`을 보내고, `filter`를 배열로 구성해
반복 query 형식으로 직렬화한다. `executedOnly`는 `includeCanceled`의 반대 값이며,
`pagingParam`도 query에 합쳐진다. 허용 필터 값·페이지 커서·응답 모델은 아직 검증하지
않았다. 따라서 기존 `range.from`·`range.to`·`size`·`number` 계약의 버전만 올려서는 안 된다.

알림에서 사라진 `/api/v1/trading/orders/histories/tab`과
`/api/v2/my-assets/orders/markets`는 현재 CLI가 호출하지 않는다.
번들 목록에서 사라진 사실과 서버 endpoint 폐기는 별도로 판단한다.

## 구현과 회귀 검증

- 미체결 조회는 `result`, 완료 조회는 `result.body`가 명시적인 배열이어야 한다.
- 누락·`null`·변경된 wrapper는 오류이며, `[]`는 정상적인 빈 내역이다.
- 잘못된 미체결 응답을 받은 `FindOrder`는 완료 내역으로 넘어가거나 주문 없음으로
  결론 내리지 않고 조회 오류를 반환한다.
- 카탈로그는 실제 호출하는 버전·시장·경로만 `implemented`로 분류한다.
  기존 완료 주문 경로는 번들 추출 누락에도 보존한다.

합성 응답을 사용하는 다음 테스트에서 수정 전 실패, 수정 후 통과를 확인했다.

```bash
go test ./internal/client -run 'TestOrderHistoryRejectsMissingLists|TestFindOrderStopsOnInvalidPendingHistory' -count=1
```

## 남은 검증

조사 시점의 WTS 세션은 `auth status`의 라이브 검사에서 HTTP 401을 반환했다.
기존·신규 주문 API의 실제 응답 호환성은 미확인이며, 신규 계약을 `verified`로
승격하지 않았다. 재로그인 후 주문 화면의 읽기 전용 요청을 캡처해 다음을 확인한다.

1. 신규 v2·v3의 실제 호스트, `accountKey` 전달 방식, 응답 배열과 필드.
2. 완료 v3의 취소 포함 여부, 필터 enum, 페이지 경계와 날짜 범위 지원 여부.
3. 기존·신규 조회의 동일 범위 결과 일치 여부. 실제 값은 저장·커밋하지 않는다.

일반 Toss Android 앱 5.276.0은 후보 버전이며, 감사된 5.275.0과 다르다는
`stale=true` 표시만 확인됐다. 이 신호로 모바일 계약이나 WTS 지원 범위를 변경하지 않는다.
