# WTS 주문 API 변경 분석 — 2026-09-14

## 결론

신규 미체결 v2·완료 v3 경로 발견은 기존 CLI 경로의 폐기를 뜻하지 않는다.
활성 빌드 `zohm1Acaa2LR63_36yS6O`에는 기존 미체결 v1과 기간별 완료 주문 v2의
호출 코드가 함께 남아 있고, 재로그인 후 두 기존 경로의 HTTP 200 응답을 확인했다.
기본 조회는 유지하고, 완료 v3를 `orders completed --all-dates`에 별도로 연결했다.

확인된 런타임 문제는 주문 목록이 누락된 HTTP 200 응답을 정상적인 빈 내역으로
처리한다는 점이다. v0.52.0에서 누락·`null` 목록을 오류로 거절하도록 수정했다.
이는 합성 HTTP 응답으로 재현한 문제이며, 실제 서버에서 같은 응답을 관측했다는 뜻은 아니다.

## 공개 번들 근거

75개 청크를 다시 수집했다. 아래 근거에는 계좌·세션 데이터가 포함되지 않는다.

| 경로 | 번들 근거 | 판정 |
| --- | --- | --- |
| `/api/v1/trading/orders/histories/all/pending` | `_app`의 module 20038 호출 함수와 module 70690 query에서 사용 | 기존 CLI 유지 |
| `/api/v2/trading/my-orders/markets/{market}/by-date/completed` | module 64370 export `cV`, module 29857의 기간별 query에서 사용 | 기존 CLI 유지 |
| `/api/v2/trading/orders/histories/all/pending` | module 64370 export `YB`, CERT GET, `accountKey` 요청 옵션, query/body 없음 | `partial` 후보 |
| `/api/v3/trading/my-orders/completed` | module 64370 export `NQ`, CERT GET, `accountKey` 요청 옵션, 필터·페이지 인자 | `verified`, 전체 기간 조회 구현 |

v3 완료 주문 호출부는 조건에 따라 `market`을 보내고, `filter`를 배열로 구성해
반복 query 형식으로 직렬화한다. `executedOnly`는 `includeCanceled`의 반대 값이며,
`pagingParam`도 query에 합쳐진다. CLI는 검증된 `executedOnly=false`, 선택적 `market`,
`size`, `number`, `key`만 사용한다. 추가 `filter` enum은 미확인이라 노출하지 않는다.
기존 `range.from`·`range.to` 계약의 버전만 올려 사용하는 방식은 아니다.

알림에서 사라진 `/api/v1/trading/orders/histories/tab`과
`/api/v2/my-assets/orders/markets`는 현재 CLI가 호출하지 않는다.
번들 목록에서 사라진 사실과 서버 endpoint 폐기는 별도로 판단한다.

## 구현과 회귀 검증

- 미체결 조회는 `result`, 완료 조회는 `result.body`가 명시적인 배열이어야 한다.
- 누락·`null`·변경된 wrapper는 오류이며, `[]`는 정상적인 빈 내역이다.
- 잘못된 미체결 응답을 받은 `FindOrder`는 완료 내역으로 넘어가거나 주문 없음으로
  결론 내리지 않고 조회 오류를 반환한다.
- 카탈로그는 실제 호출하는 버전·시장·경로만 `implemented`로 분류한다.
  기존 완료 주문 경로는 번들 추출 누락에도 보존한다.

합성 응답을 사용하는 다음 테스트에서 수정 전 실패, 수정 후 통과를 확인했다.

```bash
go test ./internal/client -run 'TestOrderHistoryRejectsMissingLists|TestFindOrderStopsOnInvalidPendingHistory' -count=1
```

## 라이브 검증과 지원 범위

사용자가 재로그인한 뒤 `auth status`의 `valid=true`를 확인했다.
`capture_post_bodies.mjs /account/orders --get`에서 CERT 호스트의 기존 미체결 v1,
신규 미체결 v2, 완료 v3 요청을 관측했다. v3의 초기 query는 `executedOnly`, `size`,
`number`였다. 실제 값은 저장·공개하지 않고 구조와 비교 결과만 확인했다.

- 미체결 v1은 `result: []`, v2는 `result: {body: [], totalCount: number}`로 응답했다.
  v2에는 비어 있지 않은 주문 행을 관측하지 못했고, 기존 v1이 정상이라 전환하지 않았다.
- 기간별 완료 v2는 국내·미국 모두 HTTP 200, 명시적인 `result.body` 배열을 반환했다.
- 완료 v3는 비어 있지 않은 `result.body`, `lastPage`, `pagingParam`을 반환했다.
  행별 `market`, 주문 식별자, 완료·취소 상태와 체결가·수량 필드의 형식을 확인했다.
- v3는 첫 페이지 `number=1`, `size=1`로 받은 `pagingParam.key`와 다음 `number`를
  보내면 다른 주문을 반환했다. `market=kr|us`의 시장 일치와 `size=100`도 확인했다.
- 실제 CLI에서 전체 기간 1·2페이지, 미국 필터, 크기 100 및 기존 기본 조회가 성공했다.

`--all-dates`는 토스가 제공하는 내역에 날짜 필터를 보내지 않는 조회다. 기본 크기는
50이며 한 페이지만 출력한다. `size`·`page`는 1–100, N페이지는 앞선 커서를 얻기 위해
최대 N번 조회한다. 빈/반복 커서·잘못된 페이지 메타데이터는 오류로 처리한다.
MCP `completed_orders`의 `all_dates`는 `from`·`to`와 함께 사용할 수 없다.
자동 감시의 `completed-orders-all-dates` probe도 같은 CERT GET 계약을 사용한다.

남은 후보는 미체결 v2의 비어 있지 않은 행과 완료 v3의 추가 필터 enum이다.

일반 Toss Android 앱 5.276.0은 후보 버전이며, 감사된 5.275.0과 다르다는
`stale=true` 표시만 확인됐다. 이 신호로 모바일 계약이나 WTS 지원 범위를 변경하지 않는다.
