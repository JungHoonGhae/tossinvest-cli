# ASC 도입 검증 — 2026-09-16

## 판정

**보조 도구로 도입, 계약 확정은 JADX·원본 DEX와 교차 확인.** 알려진 클래스의 선택 디컴파일과
코드 참조 조회가 빠르게 동작했다. 그러나 endpoint annotation의 참조 검색 누락 및 추상
메서드 인자·parameter annotation 손실이 확인돼 전체 API 탐색·검증 도구로 대체하지 않는다.

재실행 방법과 고정 의존성은 [tools/asc](../../../tools/asc/README.md)에 있다. 도구 설치와
검증은 로컬에서 완료했다. APK 실행, 계정 접근, 실서비스 호출은 없었다.

  [기존 서명 검증 완료 산출물](2026-09-02-android-static.md)과 일치하므로 같은 분석본을 사용했다.
  최신 후보 5.276.0의 감사 완료나 현재 서버 동작 검증을 뜻하지 않는다.
- ASC: [`ff1df854bb9db63066364bbb0d16484fcc72fb75`](https://github.com/MG1937/ASC/tree/ff1df854bb9db63066364bbb0d16484fcc72fb75), Androguard 4.1.3, Python 3.12.13.
- macOS arm64. 각 ASC 작업은 새 subprocess로 3회 실행했다. 파일시스템 캐시를 비우지 않았으며
  아래는 wall time 중앙값이다. 메모리는 측정하지 않았다.
- JADX 1.5.6은 같은 APK에서 `--no-res --single-class o.setRouteDatabaseokhttp`로 1회 비교했다.

## 확인된 한계

1. `findrefs string /api/v1/dashboard/all-accounts`는 `TaskQueueexecute1`의 두 코드 참조를
   찾았지만 실제 interface `setRouteDatabaseokhttp`의 endpoint annotation을 찾지 못했다.
   이는 [현재 code-item 검색 구현](https://github.com/MG1937/ASC/blob/ff1df854bb9db63066364bbb0d16484fcc72fb75/droidasc/asc_core/findrefs/scan/code_item_scan.py)과 일치한다.
2. 같은 interface의 `getclass` 출력에는 경로 annotation과 generic `Signature`가 있지만
   실제 선언은 `IAuthTabCallback()`로 출력돼 요청 body·continuation 인자 및 parameter
   annotation이 빠졌다. **source에 경로가 보인다고 HTTP 계약 전체가 보존된 것은 아니다.**
3. 일부 출력에 Java가 아닌 `None` 표현이나 부정확한 선언이 있어 그대로 컴파일할 수 있는
   소스가 아니다. 자동 코드 생성 입력으로 쓰지 않는다.
4. upstream의 일부 압축 해제 최적화는 작성자가 실험적이라고 설명했다.
   [관련 이슈](https://github.com/MG1937/ASC/issues/4). 이번 평가는 위 고정 commit의 실제 결과다.

## 도입 방식과 검증

- ASC를 포함한 49개 패키지를 전용 Python 환경에 고정 설치한다. Go/CLI/MCP 런타임에는
  의존성을 추가하지 않는다. ASC import 패치는 별도 프로세스 안에 한정한다.
- `tools/asc/verify.py`가 APK hash를 확인하고 6개 작업의 결과와 시간을 재측정한다. 필수 결과
  누락은 실패, 인자·annotation 손실은 `partial`로 남긴다. 이번 결과는 **partial**이다.
- 새 APK의 endpoint 목록·serializer 필드·인증 소유권은 기존 감사 절차대로 교차 확인한다.
  도구 도입만으로 WTS 카탈로그의 구현 상태나 Android 감사 버전을 변경하지 않는다.
- APK/디컴파일 원문은 저장소 밖의 로컬 분석 디렉터리에 보존한다. 공개 저장소에는 실행
  도구, 잠금 파일, 검증 profile, 측정 결과 요약만 남긴다.

검증 완료: 실제 APK의 18회 측정 및 최종 도구로 6개 작업 재확인, Python 테스트 118개,
`make test`, `make lint`, launcher shell 문법 검사. 이 개발 도구 도입은 배포 바이너리를
바꾸지 않으므로 별도 tossctl 버전 태그는 만들지 않는다.

검토 중 발견한 빈 profile의 허위 성공은 실행 전 profile 검증으로 수정했다. 빈 case·필수
검사·빈 문자열 및 경로 형태 case id를 거부하며, 최종 도구로 실제 APK 6개 작업을 재확인했다.
