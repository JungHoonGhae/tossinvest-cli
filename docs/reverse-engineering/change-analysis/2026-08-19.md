# API 변경 분석 — 2026-08-19

## 0. 스코프

공식 Open API spec 라이브 대조(`docs/migration/openapi.latest.json` vs
`https://openapi.tossinvest.com/openapi-docs/latest/openapi.json`, 직전 스냅샷 `7628bd2`)
전체. `info.version` 은 **1.2.14 로 불변**이고 경로·스키마 추가·삭제 **0건**,
REST 스펙의 정규화 diff 는 13줄이다.

**그런데 이번 주기의 실제 내용은 REST 스펙 안에 없다.** 토스가 **공식 실시간 웹소켓
API** 를 열었고, REST 스펙에는 그 사실을 가리키는 링크와 문장 세 줄만 들어왔다.
본체는 별도 문서 `asyncapi.json`(AsyncAPI 3.0, `info.version` **1.2.2** — REST 와 독립)
이며, 이 레포는 그 파일을 **추적하고 있지 않았다**. 이번에 `docs/migration/asyncapi.latest.json`
으로 편입했다.

## 1. 변경 요약

### (1) 헤드라인 — 실시간 웹소켓 API 출시

REST 스펙에 들어온 흔적은 이게 전부다.

| 위치 | 변경 |
|---|---|
| `externalDocs` (신규) | AsyncAPI 3.0 스펙 링크 — "구독 선언·메시지 스키마·한도·keepalive·재연결 규칙" |
| `info.description` (신규) | 실시간 스트리밍은 REST 가 아니라 `wss://openapi-ws.tossinvest.com/ws/v1`, **AsyncAPI 문서가 실시간의 source of truth** |
| `tags[Market Data].description` | "웹 소켓은 **추후 지원 예정**" → "실시간 체결·호가는 **폴링 대신 웹소켓으로 구독 가능**" |

`docs/migration/open-api.md` 의 "REST only (마케팅 페이지의 WebSocket 언급은 아직 spec 에
없음)" 는 오늘부로 사실이 아니다.

### (2) 필드 의미 변경 3건

| 위치 | 내용 |
|---|---|
| `Order.orderedAt` example | `2026-03-29T09:30:00+09:00` → `...:00.000+09:00` (밀리초) |
| `OrderExecution.filledAt` example | 동일하게 밀리초 |
| `OrderExecution.averageFilledPrice` description | "부분 체결 시 체결된 건의 평균" → 뒤에 **", 미체결 시 null"** 추가 |

밀리초는 example 만 바뀌었고 `format: date-time` 은 그대로다. 우리 파서는
`time.Parse(time.RFC3339, ...)` 인데 Go 는 **파싱 시** 레이아웃에 없어도 소수 초를 받는다 —
동작에는 영향이 없다. 다만 누가 레이아웃을 더 엄격한 것으로 갈아끼우면 조용히 깨지는
자리라 회귀 테스트를 남겼다. `averageFilledPrice` 의 null 은 이미 nullable 로 문서화돼
있던 것을 문장으로 옮겨 적은 것(`parseDecimal` → 0)이라 코드 조치 없음.

## 2. 실시간 스펙 호출법 (AsyncAPI 1.2.2)

`wss://openapi-ws.tossinvest.com/ws/v1`, handshake 시 `Authorization: Bearer {access_token}`
(REST 와 동일한 client-credentials 토큰). 토큰 없음·만료 `401`, 허용 IP 미등록 `403`.
**인증은 handshake 1회** — 연결 유지 중 토큰이 만료돼도 연결은 안 끊긴다.

### 구독 모델 — 선언형 full-replace

연결 후 JSON **배열 한 개**를 텍스트 프레임으로 보내며, 그 배열이 곧 현재 구독 전체다.
subscribe/unsubscribe 액션이 없고 **빠진 항목은 자동 해제, `[]` 는 전체 해제**.

```json
[{"id":"req-1"},{"type":"trade:us","codes":["AAPL"]},{"type":"orderbook:kr","codes":["005930"]},{"type":"personal:order","codes":["3"]}]
```

수신 프레임은 top-level `type` 으로 갈린다: `subscriptions`(ack, 데이터보다 먼저) ·
`message`(+`topic`) · `error` · `pong`.

| 채널 | topic | data |
|---|---|---|
| 체결 | `trade:{시장}:{symbol}` | `price` · `volume` · `timestamp` · `currency` |
| 호가 | `orderbook:{시장}:{symbol}` | `timestamp`(nullable) · `currency` · `asks[]`/`bids[]` (`price`·`volume`) |
| 주문 | `personal:order:{accountSeq}` | `event`(PENDING/PARTIAL_FILL/FILL/CANCELING/…) · `accountSeq` · `order`(REST 주문 조회와 동일한 스냅샷, **단 `execution.filledAt` 없음**) |

### 반드시 지켜야 하는 규칙

- **한도**: 동시 연결 계정당 2개(초과 시 **가장 오래된 연결이 끊김**) · 연결당 구독 100건
  (채널×종목 조합 기준 — `trade:us:AAPL` + `orderbook:us:AAPL` = 2건) · 선언 5회/초
  (`rate-limit-exceeded`, `Retry-After` 헤더 없음 → 약 1초 대기 후 재선언).
- **keepalive**: 서버는 **클라이언트로부터 수신이 180초 없으면** 끊는다. 서버가 보내는
  데이터는 타이머를 리셋하지 않는다 — 데이터를 받고 있어도 60초 간격으로 순수 텍스트
  `PING`(대문자, JSON 아님)을 보내야 한다. 응답은 `{"type":"pong"}`.
- **초기 스냅샷 없음**: 구독 직후엔 아무것도 안 온다. 다음 갱신부터 푸시다 — 현재 상태가
  필요하면 REST(`GET /api/v1/trades`, `GET /api/v1/orderbook`)로 먼저 채워야 한다.
- **유실 감지 불가(시세)**: sequence 가 없고 항상 최신 상태 우선. 누적 거래량·매수/매도
  구분이 없어 **수신 프레임 합산으로 누적값을 재구성할 수 없다** — 누적은 REST 캔들·현재가.
- **주문 채널은 무손실이지만 연결 세션 내부에서만**: 미소비분을 유지하고, 클라이언트가
  2초 이상 막히면(backpressure) 서버가 끊는다. 끊긴 구간 이벤트는 재전송되지 않으므로
  재연결 후 재선언 + `GET /api/v1/orders` 재동기화가 필수.
- **종료**: 서버 배포 시엔 `error.code = server-shutdown` 이 먼저 오지만, 그 외(idle 초과,
  backpressure, 연결 한도로 밀려남)는 **close code 없이** 끊긴다. 지수 백오프(1s→2s→4s,
  jitter) 재연결, 그리고 **재연결 전에 이전 연결을 먼저 닫을 것** — 안 그러면 새 연결이
  옛 연결을 밀어내는 걸 반복한다.
- 부분 거부: ack 의 `rejected[]`(`stock-not-found` · `symbol-market-mismatch` ·
  `account-not-found`)는 **원인을 고치기 전엔 재선언해도 같은 이유로 다시 거부**된다.
  나머지 항목은 정상 구독되고 연결도 유지된다.
- 주문 채널의 `codes` 는 `GET /api/v1/accounts` 의 `accountSeq` 이며 **숫자를 문자열로**
  넣는다. 본인 종합매매·활성 계좌의 국내/미국 **주식** 주문만 온다.

## 4. 도구의 세 번째 맹점

`tools/openapi_diff.py` 는 이번 변경을 **한 줄도 못 잡았다.** 세 절(신규 경로 / 필드 의미
변경 / 오퍼레이션 설명 변경)이 전부 조용했고, 출력만 보면 "밀리초 예시 + null 문구" 가
전부인 주기로 보인다. 실제로는 **새 프로토콜이 열린 날**이다.

이유: 이번 정보는 `paths` 도 `components` 도 아닌 **스펙 최상단**(`info.description`,
`externalDocs`, `tags[].description`)에만 적혔다. 새 프로토콜·별도 스펙 문서 링크는
구조상 거기로 올 수밖에 없다.

`[스펙 메타 변경]` 절을 추가했다. 이제 동작 규칙이 적히는 자리는 **네 곳**이다 —
경로 추가 · 스키마 필드 description · 오퍼레이션 description · **스펙 메타**.

두 번째 구멍은 모니터 쪽이었다. `daily-monitor.yml` 은 `openapi.json` 만 해시했으므로
AsyncAPI 스펙이 통째로 바뀌어도 아무 알림이 없었다. `asyncapi.json` 도 받아 해시하고
`asyncapi.latest.json` 으로 커밋하도록 했다(스냅샷에 `asyncapi_version`·`asyncapi_sha256`
추가). **REST 와 version 이 독립이라 REST 해시로는 대신 볼 수 없다.**

## 7. 남은 결정 — 실시간을 어떻게 낼 것인가

구현 자체보다 노출 방식이 갈린다. 최소한 이 셋을 정해야 한다.

1. **커맨드 모양**: `tossctl stream trade 005930` 처럼 채널별로 낼지,
   `tossctl stream --trade 005930 --orderbook 005930 --order` 한 개로 낼지.
   프로토콜이 **한 연결에 배열 하나(full-replace)** 라서 후자가 프로토콜 모양에 가깝다.
2. **`push listen` 과의 관계**: 공식 주문 이벤트가 상위 호환이다. `push listen` 을
   WTS 전용으로 남길지, `stream` 안에서 자격증명에 따라 라우팅(hybrid)할지.
3. **초기 스냅샷**: 구독 직후 아무것도 안 오는 게 CLI 로는 "멈춘 것" 처럼 보인다.
   붙자마자 REST 로 한 번 채우고 스트림으로 넘어갈지.

구현 시 `docs/reverse-engineering/push-events.md` 의 "Toss does not use WebSocket" 은
**WTS 웹 한정**이라는 단서를 달아야 한다 — 공식 API 에는 이제 웹소켓이 있다.
