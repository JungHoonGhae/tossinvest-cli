# API 변경 분석 — 2026-10-28

## 스코프

자동화 PR #324(`daily-monitor` 10/27 실행, 커밋 `09a48baa`)의 공식 REST 스냅샷과 `main`(10/8 스냅샷)을
`tools/openapi_diff.py --rev 09a48baa` 로 비교했다. 10/28 라이브 스펙의 전체 해시(`4e66decb…`)가 #324 와 같고,
AsyncAPI 는 1.2.2 · `176595a3…` 로 변화 없다. 같은 기간 WTS 주간 모니터(#320)는 Android 후보 버전
5.280.0 → 5.281.0 표기만 바꿨고 엔드포인트 변동은 없다.

## 변경 요약

- 버전 `1.2.24 → 1.2.24`. **버전 번호를 올리지 않고 본문만 바꿨다.** `spec_paths_sha256` 은 그대로이고 `spec_full_sha256` 만 달라졌다.
- 경로 38 → 38 (+0 / −0), 스키마 101 → 101 (+0 / −0). **삭제 0, 필드 의미 변경 0.**
- 오퍼레이션 설명 변경 1건: `POST /api/v1/conditional-orders/{id}/modify` 에 **수정 가능 상태** 규칙 추가.
  - 감시 중(`WATCHING`)·일시정지(`PAUSED`)만 수정 가능.
  - `ORDERING`·`ORDERED`·`COMPLETED`·`EXPIRED` 는 `422 modify-restricted`. 감시 중이라도 조건 충족 판정 중이면 거절될 수 있다.
  - 주문이 접수된 조건주문은 취소 후 재생성. **조건주문을 취소해도 이미 접수된 주문은 취소되지 않는다.**
- 미분류 4건: 같은 경로의 422 응답 예시(`modifyRestricted`, 메시지 "해당 주문은 정정할 수 없습니다."). 위 규칙의 예시라 별도 판정 없음. **잔여 미분류 0건.**

## 커버리지 대조

| 변경 | 기존 표면 | 판정 | 근거 |
| --- | --- | --- | --- |
| 수정 가능 상태 규칙 + `422 modify-restricted` | `order conditional modify` · MCP `modify_conditional_order` | **기존 표면 보강** | 422 가 `official.APIError` 로 원문만 통과해 사용자는 "정정할 수 없습니다" 만 봤다. 이유도 다음 조치도 없었다 |

신규 경로가 없으므로 WTS 후보 대체 여부와 `overrides` 갱신 대상도 없다.

## 함정 — 수정 응답의 새 ID 를 3개월 넘게 버리고 있었다

이번 규칙을 확인하려고 수정 오퍼레이션 설명 전체를 다시 읽다가, 2026-07-06 스냅샷(`4d1a346`)부터 있던
**"수정은 취소 후 재생성이라 새 `conditionalOrderId` 가 발급되고 기존 ID 는 무효화된다"** 를 tossctl 이 무시해 온 것을
발견했다. `official.ModifyConditionalOrder` 가 응답을 `nil` 로 버렸고 CLI 는 "수정했습니다" 만 찍었다.
사용자가 같은 ID 로 다시 조회·취소하면 404 가 나고, 새 ID 는 목록에서 찾아야 했다.

당시 차분 도구는 설명 변경을 따로 보여 주지 않았다. 지금 도구에는 `[오퍼레이션 설명 변경]` 절이 있지만
**이미 있던 설명은 차분에 다시 안 뜬다.** 쓰기 오퍼레이션을 손볼 때는 그 경로의 설명 전문을 읽는다.

## 분류

- **behavior-rule**: 수정 가능 상태 규칙. 에러 안내로 반영.
- **기존 결함**: 수정 후 새 ID 미반환. 이번 PR 에서 함께 수정.

사전 상태 조회로 막는 방식은 쓰지 않았다. 스펙이 "감시 중이라도 판정 중에는 거절될 수 있다" 고 해서 조회 결과가
보장이 아니고, 조회 한 번이 `CONDITIONAL_ORDER_HISTORY` 레이트 리밋을 쓴다. 서버 거절을 해석하는 쪽이 한 곳에서 끝난다.

## 후속 조치

- 없음. 조건주문 취소 커맨드가 "이미 접수된 주문은 남는다" 를 미리 알려야 하는지는 사용 사례가 생기면 다시 본다.

## 실행 결과 — 2026-10-28

- `official.ModifyConditionalOrder` 가 `ConditionalOrderResponse` 를 읽어 `domain.ConditionalOrderRef` 를 돌려준다.
  `hybrid` → `trading.ConditionalBroker` → `Service.ModifyConditional` → ops 핸들러·CLI 까지 같은 값을 전달한다.
  CLI 는 `조건주문을 수정했습니다. 기존 ID 는 더 이상 쓸 수 없습니다. 새 ID: <id>` 를 출력하고, MCP 는 `{id}` 를 반환한다.
- `hybrid.ModifyConditionalOrder` 가 `422` + `modify-restricted` 를 감싸 수정 가능 상태, 상태 확인 커맨드,
  "취소해도 접수된 주문은 남으니 `tossctl order cancel` 로 따로 취소" 를 붙인다. 원래 `*official.APIError` 는 `%w` 로 보존한다.
  CLI 와 MCP 가 둘 다 이 함수를 거치므로 한 곳에서 끝난다.
- MCP 요약에 수정 가능 상태와 새 ID 반환을 적었다. 목록 크기 테스트(30 000 바이트) 통과.
- 검증: `go test ./...`·`make lint` 통과. 422 안내 테스트는 안내 문구를 끈 상태에서 실패하는 것을 먼저 확인했다.
  계약 테스트는 httptest **더미 데이터**. 실제 조건주문 수정은 라이브로 실행하지 않았다(실계좌 주문 변경).
