## 요약

비교 기준은 부모 커밋이다. 이 커밋에서 바뀐 파일은 `docs/migration/.openapi-snapshot.json`과 `docs/migration/asyncapi.latest.json` 두 개이고, `docs/migration/openapi.latest.json`은 바뀌지 않았다.

- **REST(OpenAPI)는 변경이 없다.** `tools/openapi_diff.py --rev`를 실행한 결과 버전은 `1.2.28` → `1.2.28`, 경로는 39 → 39(+0/-0), 스키마는 105 → 105(+0/-0)였다. 삭제 경로와 삭제 스키마는 없고, 마지막 절은 `[미분류 변경] 없음`이다. 스냅샷의 `spec_paths_sha256`과 `spec_full_sha256`도 그대로다.
- **실질 변경은 실시간 웹소켓 스펙(AsyncAPI)이다.** 버전이 `1.2.2` → `1.2.3`으로 올랐고 `asyncapi_sha256`이 갱신됐다. 스냅샷의 `updated_at`과 `last_checked_at`은 `2026-10-29` → `2026-11-03`이다. 내용은 세 갈래다.
  1. **기존 연결 계약이 반대로 바뀌었다(위험).** 예전 스펙은 "인증은 handshake 시점 1회이며, 연결 중 액세스 토큰이 만료되어도 연결은 끊기지 않는다"였다. 새 스펙에서는 서버가 연결 중에도 토큰을 다시 검증한다. 다음 경우 서버는 새 에러 코드 `auth-revoked` 프레임(`id` 없음)을 보내고 연결을 닫는다.
     - 토큰이 만료된 경우
     - 재발급이나 삭제로 토큰이 무효가 된 경우
     - 허용 IP 목록에서 접속 IP가 빠진 경우
     - 구독 중인 계좌가 더 이상 지원되지 않는 경우

     스펙은 "만료 전에 새 토큰을 발급받아 재연결하라"고 안내한다.
  2. **신규 채널 `personal:conditional-order`가 생겼다(조건주문 실시간 이벤트).** 채널 `realtime-conditional-order`와 오퍼레이션 `subscribeConditionalOrder`·`receiveConditionalOrder`가 추가됐다.
  3. **문구가 정정됐다.** 국내 심볼 설명이 "6자리 숫자"에서 "6자리 종목코드(숫자 또는 영문·숫자, 예 `0101N0`)"로 바뀌었다. 구독 선언 원소 표는 4종에서 5종이 됐고, 구독 ack 예시·설명, `info.description`, `connection.summary`도 바뀌었다.

### 연결 수명 규칙과 REST 토큰 규칙의 결합

REST 스펙의 `POST /oauth2/token` 설명은 이번 커밋에서 바뀌지 않았다. 그 설명에는 이미 "client 당 유효한 access token 은 1 개입니다. 재발급 시 이전에 발급된 token 은 즉시 무효화됩니다."라고 적혀 있다(`docs/migration/openapi.latest.json:13282`). `expires_in` 예시는 86400초다(`openapi.latest.json:2343`).

여기에 이번 규칙을 겹치면 두 가지가 정해진다.

- **같은 API 키로 어디서든 토큰을 재발급하면, 이미 열려 있는 웹소켓이 끊긴다.**
- **연결은 접속에 쓴 토큰의 남은 수명보다 오래 유지되지 않는다.**

### 신규 조건주문 채널 계약

- `conditionalOrder`는 REST `GET /api/v1/conditional-orders/{conditionalOrderId}` 상세와 모양이 같다. 다만 최상위 `status`와 leg(`first`·`second`) `status`에 웹소켓에서만 쓰는 `CANCELED` 값이 추가됐다. 상장폐지 같은 시스템 취소도 여기에 포함된다. 취소된 조건주문은 REST 조회에 나오지 않는다.
- `event`의 값은 `WATCHING`·`ORDERING`·`ORDERED`·`COMPLETED`·`PAUSED`·`EXPIRED`·`CANCELED`·`MODIFIED`다. 스펙은 "unknown code 를 허용하도록 구현"하라고 요구한다.
- `MODIFIED`는 수정 후 id가 유지되면 1건이 온다. id가 바뀌면 2건이 온다: 이전 id의 `CANCELED`와 새 id의 수정 후 상태다.
- 이벤트 순서 규칙:
  - 주문 처리에 실패하면 같은 id로 `ORDERING` 뒤에 `WATCHING`이 올 수 있다.
  - 만료된 조건주문을 복구하면 새 id로 `WATCHING`이 온다.
  - `ORDERED` 이후의 부분 체결은 이 채널로 오지 않는다. 체결은 `personal:order`로 받는다.
  - `triggeredOrderId`는 `personal:order`의 `orderId`와 같은 값이다.
- 손실 없는 전달은 연결 세션 안에서만 보장된다. 수신이 2초 이상 막히면(backpressure) 서버가 연결을 끊는다. 재연결 후에는 다시 선언하고, `GET /api/v1/conditional-orders`를 `status=OPEN`과 `status=CLOSED`로 각각 조회해 상태를 맞춰야 한다.

### 영향 시나리오

아래는 코드 경로를 근거로 추론한 것이고, 라이브에서 확인하지 않았다.

1. **토큰 만료로 정기 절단.** 디스크 캐시 토큰은 남은 수명이 60초를 넘으면 다시 쓰인다. 그래서 `tossctl stream`이 다른 명령이 남긴 오래된 토큰으로 시작하면, 최악의 경우 1분 남짓 만에 끊긴다. 수명 예시가 86400초이므로 적어도 하루에 한 번은 강제로 끊긴다. 기본 `--retry`라면 다시 붙지만, 그 사이의 `personal:order` 이벤트는 다시 오지 않는다. `--retry=false`라면 `official: read: ...`로 종료된다.
2. **다른 곳의 재발급이 연결을 끊는다.** 같은 키로 토큰이 새로 발급되면 열린 stream이 끊긴다. 해당하는 경우:
   - `tossctl openapi login`: 토큰 캐시를 지우므로 그다음 공식 호출이 새로 발급받는다.
   - 다른 기기나 도구에서 같은 키로 발급받은 경우
   - REST 401 뒤의 `refresh`
3. **장기 실행 프로세스끼리 교대로 끊을 위험.** `tossctl stream`과 장기 실행 프로세스(예: MCP 서버)가 같은 키를 쓰면, 둘 다 메모리 캐시 토큰을 먼저 쓴다. 한쪽이 refresh하면 다른 쪽 토큰이 무효가 되고, 다른 쪽도 401 → refresh로 대응한다. 이렇게 서로 무효화하는 교대가 생길 수 있다.
   - 예전에는 stream이 handshake 이후 영향을 받지 않아 이 문제가 드러나지 않았다.
   - 이제는 REST 쪽 refresh마다 stream이 끊긴다. stream이 재연결할 때 handshake 401 → refresh가 다시 REST 프로세스의 토큰을 무효화한다.
4. **계좌 부적격.** `auth-revoked` 뒤 재연결하면, 스펙상 해당 계좌는 ack의 `rejected[]`(`account-not-found`)로 빠지고 나머지 구독은 유지된다. `--order`는 계좌 목록을 시작할 때 한 번만 조회하므로, 다시 선언할 때마다 같은 거부가 반복된다. 해는 없다.
5. **허용 IP에서 제외.** `auth-revoked` 뒤 재연결 handshake가 403을 받고 `ErrStreamUnauthorized`로 중단된다. 기대한 동작이다.

## 분류

**(c) breaking risk.** 신규 조건주문 채널은 (b) feature candidate로 함께 다룬다. 국내 심볼 문구 정정은 (a) no-op이다.

- 삭제된 경로나 채널은 없다. 하지만 이미 구현된 `tossctl stream`이 기대던 연결 계약이 반대로 바뀌었다. 예전에는 handshake에서 한 번 인증하면 토큰 만료와 상관없이 연결이 유지됐다. 이제는 토큰 만료·재발급·IP 제외·계좌 부적격이 모두 `auth-revoked` 종료로 이어진다. 이 새 종료 사유는 체결·호가·주문 등 기존 채널 전체에 적용된다.
- 현재 구현은 `auth-revoked`를 구분하지 못하고 일반 절단으로 처리한다. 기본 재연결 경로로 대부분 복구되지만 세 가지 위험이 남는다.
  - 손실 없이 와야 할 주문 이벤트의 공백이 정기적으로 생긴다.
  - `--retry=false`면 종료된다.
  - 여러 프로세스가 토큰을 재발급하면서 연결이 반복해서 끊길 수 있다.
- 신규 `personal:conditional-order`는 추가형 변경이라 기존 동작을 깨지 않는다. 현재 미지원이므로 기능 후보다.
- REST 스펙은 변경이 없다.

## 권장 후속 조치

1. **`auth-revoked`를 구분해 처리한다** (`internal/official/stream.go`).
   - `server-shutdown`처럼 `auth-revoked`를 감지해 전용 오류(가칭 `ErrStreamAuthRevoked`)로 반환하고, 로그에 원인을 남긴다.
   - `StreamWithRetry`는 이 오류에서 백오프를 키우지 않는다. 대신 무효화된 메모리 캐시 토큰을 다시 쓰지 않고 재연결한다.
   - 재연결 handshake가 403이면 지금처럼 영구 실패로 중단한다.
2. **토큰 갱신이 서로를 무효화하지 않게 한다** (`internal/official/token.go`, `client.go`, `stream.go`).
   - 401이나 `auth-revoked`로 거부된 토큰을 넘겨받는 갱신 경로를 둔다. 디스크 캐시에 다른 유효 토큰이 있으면 그것을 쓰고, 없을 때만 새로 발급받는다.
   - 그러면 시나리오 3의 교대 무효화를 막을 수 있다. REST 401 경로와 stream handshake 401 경로에 함께 적용한다.
3. **재연결 공백을 드러낸다** (`cmd/tossctl/stream.go`, i18n).
   - 재연결할 때 stderr에 "끊긴 구간 이벤트 미전달, 재동기화 필요"를 알린다.
   - `stream.long`에 토큰 만료·재발급 시 연결이 끊기고 다시 붙는다는 점을 적는다.

   - 만료 전에 미리 재연결하는 방식(기존 연결을 먼저 닫고 → 새 토큰 → 접속)은 클라이언트당 토큰이 1개라 공백을 없애지 못한다. 절단 시점을 예측 가능하게 만드는 선택 사항으로만 본다.
4. **신규 채널을 지원한다** (feature candidate).
   - `--conditional-order` 플래그를 추가한다. 기존 `client.Accounts`의 accountSeq 해석을 재사용해 `StreamSubscriptions`가 `personal:conditional-order`를 만들게 한다.

   - 연결당 구독 한도 100건에 계좌 code도 포함된다는 점에 주의한다.
5. **테스트를 추가한다** (httptest·더미 데이터).
